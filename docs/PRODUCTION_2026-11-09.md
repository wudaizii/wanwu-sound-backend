## 网关压缩导致合法保存冲突的修复

H5 原有 gzip 会把较大作品 JSON 的强 ETag 从 `"work:test:r3"` 变为 `W/"work:test:r3"`。客户端原样回传 If-Match，服务端按强版本比较正确拒绝，结果却是用户没有并发修改也保存失败。小草稿低于压缩阈值时不会暴露此问题。

共享 API proxy include 现在明确使用 `gzip off`、`proxy_set_header Accept-Encoding ""`；两个 API host 均保留强版本，前端静态 JS 仍实际返回 gzip。没有放宽 If-Match 校验，没有修改前端或业务容器。

新回归在本机真实 Nginx 的 http{} 启用 JSON gzip，再验证大响应的强 ETag 和下一次 If-Match。修复前精确复现弱 ETag 失败；修复后两个 HTTPS host 的 19 项检查通过。线上完整配置检查后只平滑 reload，实际大作品读回的版本标记恢复正确，后台保存／混音随后通过。

线上 snippet 与仓库模板的 SHA-256 一致，见上表。应用版本和网关配置分别追溯；未来套用模板时必须保留该修复。不要在 API 中接受弱 If-Match 来绕过并发保护。
